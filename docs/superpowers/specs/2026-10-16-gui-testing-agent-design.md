# 面向电商业务的 GUI 自动化测试 Agent 设计

本项目服务电商研发和 QA 团队：把需求、业务规则和测试目标转成可执行回归用例，在 UI 改版、弹窗和设备差异下持续执行，并以独立的业务校验发现缺陷。模型训练围绕元素定位、下一步动作、异常恢复和测试断言展开。

状态：规划建议，尚未实施。调研日期：2026-10-16。电商场景、Android 优先、人员与周期是方案假设，用户已选择 GUI 自动化测试方向，但尚未指定业务系统和算力。

## 业务范围与成功标准

首批场景包括商品搜索、SKU 选择、购物车数量、优惠券使用门槛、应付金额、地址选择、提交订单与取消订单。举例：299 元商品满足满 200 减 30 规则，应付金额应为 269 元；若界面显示 269 元而订单记录为 299 元，也应判为产品缺陷。金额全部以整数分计算。

业务载体采用本地部署的 [mall-app-web](https://github.com/macrozheng/mall-app-web) 与 [mall](https://github.com/macrozheng/mall)。前者的公开说明提供 H5 与小程序启动方式，并覆盖商品、购物车、优惠券、订单等页面。首期通过 Android Chrome 操作本地 H5 商城；这不等同于原生 App 覆盖。原生 GUI 通用能力另用 AndroidWorld 评测。原生商用 App 接入和退款全流程属于后续范围；退款页面、支付回调模拟若上游缺少，需单列扩展任务。

测试环境必须有可重置的数据、已知正确版本和可控制的故障版本。所有订单、支付状态与账户均使用测试数据；不依赖公共演示站的共享状态。

计划目标，均待项目实验验证：

| 指标 | 定义与目标 |
| --- | --- |
| 正确版本任务完成率 | 在预留业务任务上，经独立 oracle 校验的 pass@1 ≥85%；不得只靠模型自报成功 |
| 已知缺陷检出率 | ≥30 个有可达测试路径的缺陷实例，每例重复 3 次；相关失败断言检出的运行数 / 全部预定故障运行数 ≥80%；普通操作失败不算检出，也不能取三次中最好一次 |
| 产品缺陷误报率 | 已知正确版本被错误判为产品缺陷的运行数 / 正确版本全部运行数 ≤5% |
| 可判读运行比例 | 有完整证据归入 PASS、PRODUCT_FAIL 或 AGENT_BLOCKED 的运行 / 全部预定运行 ≥95%；INFRA_ERROR、INCONCLUSIVE 单列，不能通过剔除它们改变分母 |
| UI 变化适应能力 | ≥30 个事先验证会打断固定参考路径、但不改变业务语义的 UI 变化实例，每例重复 3 次；实际中断后恢复且完成全部必要断言的运行数 / 全部预定变化运行数 ≥70% |
| 成本与维护 | 按同一设备、用例、重试和模型计费口径，与未训练模型、Midscene 基线比较，不预先承诺降本比例 |

| [LlamaFactory](https://github.com/hiyouga/LlamaFactory) | 多模态 SFT、LoRA、偏好优化等；Apache 2.0 | 训练与实验配置 | 任务数据、坐标格式及运行环境适配 |

选型建议：新建项目，通过 SDK 接入 Midscene，训练部分采用 Python 与 LlamaFactory。MobiZen、UI-TARS 作为可替换模型与对照，不把多套执行框架同时合并。UI-S1 的旧依赖与主训练环境使用独立容器。

Midscene Test 当前文档标为 Beta；首期采用 SDK 与项目自己的用例协议，避免把核心数据协议绑定到 Beta YAML 格式。[官方说明](https://github.com/web-infra-dev/midscene)

Midscene 的计划缓存不等于 Android 的免模型执行。官方说明 DOM 定位缓存仅限 Web，查询和断言也不会缓存。移动端仍需定位与重新校验；稳定流程可保存为带前置条件的操作模板。[缓存说明](https://midscenejs.com/caching)

## 架构与接口职责

流程：需求和规则 → 候选用例 → 人工确认的用例集 → 环境准备 → 规划与定位 → GUI 动作 → 独立结果判定 → 报告 → 训练数据筛选 → 模型版本评测。

第一版使用一个有明确状态的控制循环。需求分析、动作策略、断言服务是职责边界，不要求为每个职责再部署一个 Agent。

- 用例生成：读取需求、业务规则和已知测试点，生成前置条件、测试数据、步骤、断言和需求引用。通过人工确认后才能进入固定验收集。
- 测试执行：TypeScript runner 使用 Midscene 运行基线，并提供学生模型的单步模式。学生模型输出规范化 Action，直接交给确定性设备适配器，不再交回另一个规划模型重写。
- 模型服务：学生模型用 vLLM 推理；输入为当前截图、任务目标与有限动作历史，输出动作类型和参数。Midscene 与学生使用不同的模型输出适配器，不能假设它们的 JSON 格式天然一致。
- 业务判定：独立 oracle 根据冻结规则校验界面提取值与测试后端状态。LLM 可提取文本或判断视觉状态；金额和订单状态由代码校验。oracle 的预期结果、故障开关、评分脚本不暴露给动作策略。
- 环境服务：按 run_id 隔离测试用户、订单和库存。数据重置在设备租约释放前完成；重置失败的设备隔离后才可接新任务。
- 轨迹存储：截图存文件/对象存储，元数据写 JSONL/Parquet。首期采用 SQLite 记录运行索引，规模增加后再迁移。
- 报告：每个结果附原始截图、动作、业务断言、环境状态、模型/数据/用例版本、延迟、token 与重试记录。

运行预算：每例最多 40 个 GUI 动作、300 秒、2 次恢复尝试；恢复尝试计入动作与时间预算。评分时不能在重试中丢弃失败运行。模型请求超时、设备断连和执行超预算分别记录。

结果状态采用 PASS、PRODUCT_FAIL、AGENT_BLOCKED、INFRA_ERROR、INCONCLUSIVE。每例在人工确认时冻结非空的必需断言 ID 集与 GUI 必经步骤，并为各断言登记生效的前置条件。判定规则如下：

- PASS：所有必需断言均有充分证据且成立，GUI 必经步骤完整。
- PRODUCT_FAIL：至少一个业务断言的前置条件、相关 GUI 动作和产品违约结果已被独立证据证实。该缺陷阻断的后续断言标记为 blocked_by_product_defect，仍可判产品缺陷并计入可判读运行；无需为取得其余证据继续操作。
- AGENT_BLOCKED：证据明确显示模型误点、无效动作、超出预算等策略执行失败，尚无充分产品缺陷证据。保留失败动作与截图，计入可判读运行，但不计入产品缺陷检出。
- INFRA_ERROR：基础设施故障导致无法继续，且此前尚无足以作出上述判定的证据；INCONCLUSIVE：现有证据不足或矛盾。若之前已证实产品缺陷，后续基础设施异常单列为 incident，不覆盖已证实结果。

缺少任一必需证据不能 PASS；证据缺失也不能自动等同于策略失败。业务 API 只供环境准备和独立 oracle 使用，不能代替被测 GUI 必经步骤。自愈只调整定位和执行路径，不允许修改断言、预期金额或跳过必要测试步骤。

## 数据设计

每步保存 schema_version、run_id、episode_id、case_id、template_id、split、app_version、device_profile、policy_version、prompt_version、step_index、截图哈希、原始尺寸、裁剪/缩放变换、动作、参数、动作前后状态、耗时和人工标签。最终标签包含独立 oracle 证据和失败原因。

内部坐标统一为原始截图上的 [0,1] 归一化坐标；执行前按尺寸还原。各模型的像素或 0–1000 坐标由独立适配器转换。系统状态栏、浏览器地址栏、裁剪区域、横竖屏变化必须记录变换，不能简单按新尺寸缩放旧坐标。

训练输入只能含当时可见的信息。最终 oracle 结果可以筛选样本和产生偏好标签，不作为策略输入。保存截图、动作和简短可验证标签，不依赖收集模型私有思维过程。

训练数据来源：

1. [CMGUI](https://huggingface.co/datasets/alibabagroup/CMGUI) 的训练部分。数据卡列出约 18k 轨迹和 98k 步，含中文操作和框标注；数据许可为 CC BY 4.0，与仓库代码许可分别记录。
2. 测试业务系统内的人类演示与教师模型轨迹，先采集 100 条进行质量审查，再扩展至 1,000–3,000 条轨迹目标。
3. 失败与修复样本：遮挡、弹窗、相似按钮、分辨率变化、页面加载、错误订单和金额不一致。保留失败轨迹，但不把错误动作当作正确 SFT 标签。
4. 故障版本提供断言正负样本。训练、验证和测试故障按故障家族隔离，避免仅记住一种开关。

业务用例规划为 100 个模板：60 训练、20 验证、20 测试。先按模板和业务规则组合划分，再产生数值、文案和设备变体。不能先生成大量相似截图再随机分行划分。公共数据沿用官方 split，并对跨来源截图与模板重复做检查。

模型实验按顺序进行：

1. 固定环境与用例，记录现成模型和未训练学生基线。
2. 用 Qwen/Qwen3-VL-4B-Instruct 作初始学生模型，通过 LoRA SFT 学习定位与下一步动作；训练前冻结模型 revision 和图像处理配置。[模型卡](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct)
3. 对比“仅公开数据”“公开数据加业务数据”“再加修复数据”。验证集选择混合比例，测试集只作最终评估。
4. 在同一输入状态构造正确/错误动作偏好对，开展多模态 DPO；不要将不同前缀的两整条轨迹直接拼成偏好对。
5. 可选：SFT 已有可靠收益且环境吞吐足够时，采用 UI-S1 作半在线 RL 对照；真实在线 RL 需另加环境 reset/step 与奖励适配。成功奖励以完成必要步骤并经业务 oracle 验证为条件，不能奖励随意点击或仅自报完成。

主要实验保持相同用例、设备配置、预算和模型解码参数；Midscene 与原生学生 action loop 的框架差异单列报告。首次公开基准成绩也可能受基座模型既有训练影响，不宣称全新无污染的泛化结论。

## 评测矩阵与资源

业务盲测：20 个预留模板 ×3 个业务数据种子 ×3 个屏幕配置 ×3 次独立重复，共 540 次运行/模型。三种屏幕配置是测试配置，不等同于三种真机兼容认证。

缺陷评测：至少 30 个预留故障实例，每个实例有人工确认的可达测试路径与独立预期结果，3 次重复，共至少 90 次/模型。检出率以全部预定故障运行数作分母，基础设施或策略失败留在分母，另报其数量；按实例的统计仅作补充。

UI 无害变化另设至少 30 个实例，每例 3 次重复。冻结变化清单前，用已成功的参考路径证明变化会打断该路径且不改变业务结果。每次变化运行与同任务、种子、设备的无变化运行配对；不能按待评学生模型的表现事后挑选实例。恢复率以全部预定变化运行数作分母，只有实际发生中断、有限恢复后完成全部必要断言才计成功。无需恢复即完成的运行单列为适应成功，不进入恢复成功分子。测试集阶段开始前冻结训练和模型选择，结果报告给出样本数与置信区间。

资源规划假设：1 名全职开发者、QA 或业务同事每周提供约半天规则与标注审查、12–16 周。开发机建议 32GB 以上内存并支持硬件虚拟化；Android 模拟器与一台真机作联调。训练优先用 Linux GPU 主机；3B–4B VLM 的 LoRA 可先用一张 48GB GPU 做容量试验，这是资源预算建议而非显存保证。图像分辨率、多图历史和序列长度必须实测；RL 的算力与环境吞吐单独评估。GPU/API 费用按第一批 100 条轨迹的实际消耗估算。

## 交付物

交付一个可复现的本地测试环境、一套 100 模板业务用例、可重放轨迹及版本清单、一个训练后的学生模型或 LoRA adapter、四组数据消融实验、独立缺陷检出报告和 CI 回归示例。模型收益不满足预期时如实保留结果，不能用界面演示替代训练结论。
